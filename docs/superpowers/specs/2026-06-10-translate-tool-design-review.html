审查报告 — Translate Tool Design Spec

审查对象：docs/superpowers/specs/2026-06-10-translate-tool-design.md（行号引用以该文件为准）
审查日期：2026-06-10 · 所有涉及现有代码的断言均已在仓库中核实
总体评价：spec 整体质量较高——范围收敛、决策有据、错误处理和测试覆盖都想得比较细。 但存在 3 个高优先级设计冲突（Smart flip 与 Swap 的组合会产生错误的语言状态、长输入截断被当作成功、简繁映射缺失）， 以及若干前后矛盾和未定义边界。建议在进入 plan 阶段前先修订这几处，否则实现时必然要回头改 spec。

高优先级

高1. Smart flip 与 Swap 组合后，语言选择器与实际内容脱节

位置：Behavior「Smart flip」（L60–64）×「Swap」（L74–78）

Smart flip 由模型在 prompt 内决定，发生与否 UI 无从得知；而 Swap 基于当前选择器交换语言并把上次译文搬进输入框。两者组合会产生错误状态：

走查：source=Auto，target=English，用户输入英文。模型触发 smart flip，输出简体中文译文。 此时点 Swap：① 输入框被填入中文译文；② 新 source = 旧 target = English；③ 源是 Auto，按规则用启发式检测结果——检测的是原英文输入，Latin → English，所以新 target = English。 最终状态：source=English / target=English / 输入框是中文——三处全错。

建议（三选一，写进 spec）：

  • 方案 A（推荐）：把 flip 判定从模型挪到客户端——用脚本启发式判断"输入语言 ≈ target"后由客户端改写 prompt 中的实际 target，并在 UI 上反映真实方向（如目标选择器旁显示流向提示）。zh↔en 主场景下 Chinese/Latin 的区分足够可靠，且 UI 永远知道真实方向，Swap 自然正确。
  • 方案 B：保留模型 flip，但 Swap 不再依赖选择器，而是对上次输出跑同一个启发式来确定新 source，对应推导新 target。
  • 方案 C（最小代价）：v1 规定：上一次 run 的 source 为 Auto 时，Swap 只交换语言、不搬运文本（或直接禁用），并在 spec 写明这是已知限制。

高2. 长译文静默截断会被当作"成功完成"记入历史

位置：Decisions「Input size」（L29）× 「不设 max_tokens」（L134–135）× SSE 解析范围（L152–155）× History（L92–93）

三条决策叠加形成漏洞：

  • 允许 20,000+ 字符输入（确认后照发，不拆分）；
  • 不设 max_tokens，由 provider 默认值兜底——DeepSeek 等供应商的默认输出上限通常远小于 2 万字符译文所需的 token 数；
  • SSE 解析"只看 delta.content 和 [DONE]"——finish_reason 被归入忽略范围。

结果：译文在中途被供应商截断（finish_reason: "length"），流仍以 [DONE] 正常结束，UI 视为成功完成，残缺译文被记入历史，用户毫无察觉。这对长文翻译这一被 spec 明确支持的场景是正确性问题，不是边角。

建议：把 finish_reason 移出"忽略"清单——解析它，length 时在输出区显示"译文被模型输出上限截断"的警告，且不记入历史（与 stall 的处理对齐）。可选：长输入时主动设置较大的 max_tokens。同时在 Testing 一节补充 finish_reason: length 的解析用例。

高3. 启发式只报 "Chinese"，Swap 无法映射到 zh-Hans / zh-Hant

位置:Detection hint（L70–73）× Swap（L74–78）× Languages（L50–56）

语言列表区分 zh-Hans 与 zh-Hant，但启发式被明确限定为只报告粗粒度类别（Chinese/Japanese/Korean/Russian/Latin/Unknown）。Swap 规则只定义了 "Latin maps to English"，检测结果为 Chinese 时映射到哪个 id 没有定义——而这是该用户群（zh↔en）最高频的路径。

建议：在 Swap 规则中补一张完整映射表：Chinese → zh-Hans（主场景默认）、Japanese → ja、Korean → ko、Russian → ru、Latin → en、Unknown → 禁用。不要尝试用码位区分简繁（共用字太多，不可靠），直接文档化"繁体用户需手动选择"即可。

中优先级

中4. "Display-only" 措辞与 Swap 的功能性依赖自相矛盾

位置：L73「Display-only; the smart-flip decision belongs to the model」 vs L76「swap uses the heuristic-detected language」

前一条说启发式纯展示，紧接着的下一条就把它用于两个功能决策：决定 Swap 后的语言、决定 Swap 是否禁用。读者（和实现者）会困惑哪句是对的。

建议：改措辞为"启发式不参与 smart-flip 判定（归模型），但参与 Swap 的语言推断与可用性判断"。若采纳问题 1 的方案 A，则此句需要整体重写。

中5. 30 秒首字节超时与自身支持的场景冲突；"valid SSE chunk" 范围未定义

位置：Error handling「Stream stall」（L224–225）× Decisions「Input size」（L29）
  • spec 一边允许 20,000+ 字符输入和本地 Ollama 端点，一边规定"首字节也适用 30 秒超时"。大 prompt 在慢供应商或本地小模型上的首 token 延迟超过 30 秒并不罕见——会把合法请求误杀。
  • "Reset the timer after each valid SSE chunk"：reasoning 模型思考期发送的 reasoning_content 增量被解析器"忽略"，SSE 注释行（: keep-alive）也可能出现——它们算不算"valid chunk"、是否重置计时器，没有定义。若不算，reasoning 模型几乎必然触发 stall 误判。

建议：① 区分两档：首字节超时放宽到 60–120 秒，chunk 间隔保持 30 秒；② 明确"任何收到的 SSE 数据（含被忽略的字段、注释行）都重置计时器"——'忽略'只指不渲染，不指不计为活动信号。

中6. source = target 是否允许未定义

位置：Behavior「Smart flip / Polish exception」（L60–69）

Polish 的"同语种润色"目前只能经由 Auto + 模型判定触发。用户最自然的表达方式是显式选 English → English + Polish，但 spec 没有说 UI 是否允许 source = target；而其余五种 style 下同语种"翻译"又没有意义。另外问题 1 的走查表明 Swap 也可能制造出 source = target 的状态。

建议：明确规则，推荐：允许 source = target，此时除 Polish 外的 style 下 Translate 按钮禁用并显示提示；Polish 下正常执行同语种润色。

中7. Swap 的两个边界未定义

位置：Behavior「Swap」（L74–78）
  • 没有上次译文时："moves the last translation into the input"——首次使用、或刚 Clear 过时没有译文，此时 Swap 是仅交换语言、还是清空输入、还是禁用？未定义。
  • 当前输入的去向：Swap 用译文覆盖输入框，原输入直接丢失。这是 DeepL 的惯例、可以接受，但 spec 应明确说"原输入被丢弃"，避免实现者自行发挥（比如塞进 history 造成污染）。

建议：补两句：无译文时仅交换语言选择、输入保留；有译文时原输入被丢弃，不进历史。

中8. 流式期间允许编辑输入但禁用 Clear —— 防护不完整

位置：Run snapshot（L83–84）× Output lifetime（L86–87）

流式期间用户可以继续编辑输入（spec 明确允许），那么全选删除就等价于 Clear 清空输入——禁用 Clear 按钮防住的其实只有它"顺带清空输出"的副作用，但 spec 没有说明这一动机，读起来像矛盾。

建议：二选一：① 在 spec 写明禁用 Clear 的原因是其输出清空副作用与正在流入的输出冲突；② 改为流式期间 Clear 仅清输入、不动输出（更一致，推荐）。

中9. partial output 与 inline error 的共存渲染未定义

位置：Error handling 开头（L214–215）× Stream stall（L224–226）

"每个失败渲染为输出窗格内的 inline error" 与 "stall 后已有 partial output 保持可见" 同时成立时，错误信息和半截译文如何共处一个窗格？错误是替换文本、还是横幅？Copy 按钮此时复制的是译文还是连错误一起？均未说明。

建议：明确：partial output 保留在输出区，错误以横幅形式显示在输出区底部（或 footer 状态区），Copy 只复制译文文本。

中10. "Persistence" 措辞误导：useToolInput 并不跨重启持久化

位置：Behavior「Persistence」（L96–97）；已核实 src/App.tsx:55-61 与 src/core/store.ts:156

该条把"input text via useToolInput("translate")"和"persist across restarts like other tools"写在同一句里，暗示输入跨重启保留。但现状是：App.tsx 的 store 订阅只持久化 favorites / theme / language / hotkey / diff，toolInputs 仅存内存——切换工具时保留、重启即失。

建议：拆开表述："输入文本经 useToolInput 在会话内保留（与其他工具一致，不跨重启）；语言/style/provider 设置经 translate slice 跨重启持久化"。顺带提醒：translate slice 需要在 App.tsx 的 hydrate 和 subscribe 两处接线，spec 的"like the diff slice"已隐含但 plan 阶段别漏。

中11. i18n 矛盾：Auto-detect 与 detected 类别名需要本地化

位置：i18n（L201–204）× Languages（L50–56）× Detection hint（L70–73）

"语言名以母语书写、是常量不走 i18n"对真实语言成立,但有两个例外被一并归入了常量：

  • Auto-detect 不是语言、没有"母语写法"，中文界面下必须显示"自动检测"；
  • detected: <language> 提示中的粗粒度类别名（Chinese / Latin / Unknown…）同样需要随界面语言变化。

建议：明确：auto 条目的 label 和检测类别名走 i18n key，其余语言名保持母语常量。

中12. normalize 对空字符串 model 的行为未定义

位置：State & persistence（L180–184）× Settings（L109–114）

"OpenAI/Custom model … preserved as strings when present"——空字符串算不算 "present"？用户清空 OpenAI 的 model 字段后，请求会带 "model": "" 发出，必然 400。Custom 的空 endpoint 有校验兜底（L228–229），空 model 没有。

建议：补充：OpenAI model 为空白时回退默认 gpt-5.2；Custom model 为空白时与无 API key 的预设同等处理——阻止发送并给出 Settings 引导提示。

低优先级

低13. 事实错误：__TAURI_INTERNALS__ 检测不在 storage.ts

位置：Architecture 表 client.ts 行（L129）；已核实 src/core/services/runtime.ts:7

spec 写 "detected via __TAURI_INTERNALS__, same as storage.ts"，但该检测实际封装在 src/core/services/runtime.ts 的 helper 中，storage.ts 里没有这段代码。

建议：改为 "reuse the isTauri helper from src/core/services/runtime.ts"——既纠正出处，也避免实现者重复造检测逻辑。

低14. capability https://** 与"只访问用户配置端点"的承诺存在差距

位置：Overview（L13–15）× Native side（L193–197）× Documentation changes（L248–250）

Overview 承诺"network calls … only to the user-configured provider endpoint"，但 Tauri capability 是静态声明，https://** 实际允许 WebView 访问任意 HTTPS 域——真正的约束只存在于应用层逻辑。Custom 端点的存在决定了 capability 没法收窄，这本身没问题，但写进 AGENTS.md 的安全例外不应给出比实际强的承诺。

建议：在 AGENTS.md 例外条目里如实分层表述："capability 层放开 https + loopback http；'仅访问配置端点'由应用层代码保证"。这样后续安全审查不会被文档误导。

低15. pushHistory 按 input 去重的副作用未提及

位置：History（L92–95）；已核实 src/core/services/history.ts:7-9

现有 pushHistory 会把相同 input 的旧条目去掉。同一段文字先翻英文、再翻日文（或换 style 重翻），历史里只剩最后一次。鉴于 restore 本来只恢复 input，影响有限，但 spec 说"standard useHistory"时应意识到这一行为是契约的一部分。

建议：在 History 条目加一句"同一输入的多次翻译在历史中仅保留最近一次（沿用 pushHistory 去重语义）"，确认这是接受的取舍。

低16. 两处小的未定义状态

位置：Trigger（L79–81）× Target pane footer（L44–46）
  • 流式期间按 ⌘↵：按钮已变成 Stop，那么快捷键是触发 Stop 还是 no-op？建议与按钮一致 = Stop。
  • footer 状态只定义了 ● streaming… 和 stopped，成功完成后显示什么（done？清空？）未定义。

低17. 顶栏布局在窄窗口下的风险

位置：Layout（L30、L36–38）

窄窗口下两个 pane 改为堆叠,但顶栏要同排容纳 6 项 style 分段控件 + history 按钮 + Translate 按钮（六个 style 的英文标签合计已相当宽，中文界面更甚）。spec 对 pane 的响应式有交代，对顶栏没有。

建议：补一句窄窗口下顶栏的降级策略——style 分段控件改为下拉、或允许横向滚动/换行。
